# WMS 仓储项目 · 版本路线图（V1.0 → V3.0）

> **基线日期**：2026-11-08
> **唯一主线**：`wsm_cloud/` 微服务版（Gateway + Nacos + 6 服务）。单体 `wsm_backend/` 已于 2026-11-08 从仓库移除，需要时按 `git checkout fa1fa24 -- wsm_backend` 取回；本地源工程仍保留，不再作为发布口径。
> **编号体系**：代码生成器 V7.x、架构拆分 V8.0 属于「工程能力」版本号，已冻结；本文档从**业务版本 V1.0** 起算，与那两条线不混用。
> **本文与 `WMS-V1.0-业务闭环-规划.md` 的关系**：那份是 V1.0 的开工前设计（已交付，作为历史基线保留）；其中 3.2 节「业务只写单体」的决策已被 2026-11-07 的方向调整覆盖——业务闭环最终迁入 cloud，单体下线。

---

## 0. 一页结论

| 版本 | 定位 | 状态 | 一句话验收 |
|---|---|---|---|
| **V1.0 业务闭环** | 让数据之间产生因果 | ✅ 已交付 2026-11-07 | 收货上架后库存自动变、发运后自动减，e2e **118/118** |
| **V1.1 可信闭环** | 不加功能，只把闭环变成「不可绕过、可证明、可重建」 | 🎯 **建议下一版** | 全新机器一键建库启动；人工改不动数量；50 线程抢 100 件不超卖 |
| **V1.2 作业补全** | 把 V1.0 规划里的 P1 真正落地 | 📋 规划 | 调拨/波次/报表/打印全部走库存唯一入口，流水恒等式仍成立 |
| **V2.0 生产可用** | 消除共库拆分与无 XA 的架构缺口 | 📋 规划 | 事务消息 + 库存独立库 + 网关鉴权 + 门禁化 CI |
| **V3.0 现场与集成** | PDA、追溯、计费、外部对接 | 💤 有真实场景再启动 | 先有硬件/客户，再做功能 |

**排期原则**：V1.1 是"还债版"，必须排在 V1.2 之前。当前 4 条闭环已经能跑，但**编辑页仍可直接改数量与状态**、**并发验收还没做**、**跨服务提交存在已知缺口**——在这三点没闭合前加调拨/波次，只会把不确定的语义复制到更多表上。

## 1. V1.0 基线（已交付，语义冻结）

### 交付内容

| 层 | 内容 |
|---|---|
| 后端 | `InventoryCoreService`（库存唯一写入口，6 方法均写流水）、FEFO 分配、入库/出库/盘点三条闭环、状态机、幂等键 `wms_request_log`、`/internal/**` 内部接口 |
| 前端 | `src/api/wms_biz.js`（10 个业务端点）+ `src/components/biz/` 5 个组件，嵌入入库单/出库单/盘点单/库存 4 页 |
| 数据 | `docs/sql/V1.0__wms_inventory_core.sql`（生成列口径改 `on_hand - allocated - locked`、幂等 DDL）、`V1.0__wms_seed.sql` |
| 工程 | `scripts/cloud-up.sh` / `cloud-down.sh` / `e2e-cloud.mjs`；全站 21 页 0 异常响应 0 JS 错误 |
| 验证 | e2e 连跑两次 **118/118**：网关边界、三条闭环、FEFO 切片、幂等回放、`qty_after-qty_before=qty_change`、可用量恒等式、单据终态 |

### 方向调整记录（重要）

V1.0 开工前的设计结论是「业务只写单体，cloud 保持骨架」，理由是共库双写会冲突。2026-11-07 按用户要求改为**业务闭环整体迁入 cloud**：库存写入口只存在于 `wms-inventory` 一个进程，入库/出库经 Feign 调用，单体随之于 2026-11-08 下线。这一步解决了"两套逻辑"，但把**跨服务事务**问题变成了主矛盾（见 §2 V1.1-6）。

### 已知边界（V1.1 的输入）

1. **共库 + 无 XA**：本地事务只覆盖自己的表，库存写入是独立远程提交；远程成功、本地提交失败会多出一笔库存，目前只能靠恒等式对账 + 盘点修正（`README.md`「一致性边界」已显式记录）。
2. **内部令牌取默认值**：`X-Internal-Token` 默认 `wms-internal`；网关不路由 `/internal/**`，但生产环境应换 mTLS/签名。
3. **数据库口令有开发默认值**：`${DB_PASSWORD:root}`，公开仓库里必须靠环境变量覆盖。
4. **17 个页面仍是 CRUD 空壳**：只有 4 页接了业务端点；主数据页保持生成器原样，这是预期，不是缺陷。
5. **e2e 绕过验证码**：登录验证码是图形算术题，脚本按集成测试同构方式直接插 `sys_session`，其余鉴权链路真实。
6. **明细查询按前端筛选**：生成器 `/page` 的 DTO 没有按单据 ID 过滤的字段，弹窗拉全量明细后前端筛（最多 10 页 × 200 行）。

## 2. V1.1 可信闭环（P0，建议立刻做）

**目标**：不加任何业务功能，把 V1.0 的"能跑通"升级为"跑得对、拦得住、重建得出来、并发下不塌"。

| 编号 | 项 | 现状 / 证据 | 交付物 | 二值验收 |
|---|---|---|---|---|
| **V1.1-1** | 建库脚本归位 | 删除单体时 `init_*.sql` 5 个脚本一并被删，仓库一度只剩 `dict.sql`；**已于 2026-11-08 从 `fa1fa24` 恢复到 `wsm_cloud/db/`** | `db/init_tables.sql` / `init_seed.sql` / `init_menu.sql` / `init_sys_user.sql` / `init_sys_flow.sql` / `dict.sql` | 全新 MySQL 按 README 顺序执行，能建出 21 张业务表 + 系统表 |

## 3. V1.2 作业补全（继承 V1.0 规划 P1）

**前提**：V1.1 全绿。**目标**：把 21 张表里已经预留、但还没有因果关系的作业域补全。

| 功能 | 要点 | 为什么放在这一版 |
|---|---|---|
| **调拨闭环** | 同仓移库（一条出 + 一条入流水）、跨仓在途（`lock_type=TRANSFER`，`qty_locked` 已计入可用量） | 表 `wms_transfer_order` 已存在，冻结/解冻能力 V1.0 已具备 |
| **波次与拣货任务** | 按承运商/区域合并多张出库单 → 生成波次 → 拆分拣货任务；任务确认仍走 `pick` 端点 | `wms_wave` / `wms_pick_task` 已建表，出库闭环已稳定 |
| **报表** | 收发存汇总（SKU/仓库/时间段）、库龄、周转率、呆滞料；只读，从流水表出而不是从单据表拼 | 流水是 V1.0 的副产品，数据可信度已由恒等式保证 |
| **单据打印** | `printPage.ftl` 模板已在生成器里，接上单据 + 明细数据出入库单/拣货单 | 无新业务逻辑，纯展示层 |
| **效期预警** | 按 `expiry_date` 与 `idx_expiry` 做到期/临期看板 | FEFO 已按效期选批，查询侧补齐即可 |

**验收**：新增功能全部经过 `InventoryCoreService`，`on_hand = Σ qty_change` 恒等式在每条路径成立；e2e 从 118 扩到约 150 条断言；报表数字与流水合计逐项对得上。

## 4. V2.0 生产可用（架构升级，不改业务语义）

| 项 | 现状 → 目标 |
|---|---|
| **事务一致性** | 本地事务 + 远程独立提交 → **事务消息（RocketMQ）或本地消息表 + 定时补偿**，消除"多出一笔库存"的固有缺口 |
| **数据库** | 6 服务共 `wms_warehouse` 一库 → 至少把库存中心独立成库；进一步按域分库，跨库查询走接口而非 JOIN |
| **鉴权** | 各服务本地校验（共库 `sys_session`）→ 网关统一鉴权 + 服务间 mTLS/签名；引入角色体系（`BuiltinFlowService` 里已有 TODO：当前无角色恒放行） |
| **可观测** | 靠日志排查 → 链路追踪、库存变动审计看板、慢 SQL 与恒等式偏离告警 |
| **CI/CD** | 手工 `mvn package` + 手工 e2e → 流水线跑 V1.1-8 门禁，tag 才能发版 |
| **配置与安全** | 明文默认值 → 配置中心 + 密钥托管，全环境无默认口令 |

**验收**：注入一次远程提交失败/服务宕机，库存与单据仍最终一致；单个业务服务挂掉不影响其他域；门禁流水线可在干净环境复现全部结果。

## 5. V3.0 现场与集成（P2，有真实场景再启动）

沿用 V1.0 规划的判断，**没有真实硬件或客户前做了也是空转**：

## 6. 贯穿所有版本的六条铁律

1. **库存变动只有一个门**：任何绕过 `InventoryCoreService` 直接 `updateById` 改 `qty_*` 的代码，评审一律驳回。
2. **有变动必有流水**：`qty_after - qty_before = qty_change`，恒等式是每版 e2e 的最后一条断言。
3. **状态机集中管理**：合法转移写在 `DocStateMachine`，IllegalState 直接抛业务异常，不允许散落 `if (status == ...)`。
4. **业务端点幂等**：新增的每个写端点必须接 `requestId` + `wms_request_log`，重复提交返回上次结果。
5. **前端不写数量字段**：主数据页可编辑，单据页的数量/状态只读，由业务端点写入（V1.1-3 落地后成为硬规则）。
6. **雪花 ID 全程字符串**：`Map<String,Object>` 返回值里的 Long 必须 `String.valueOf(...)`，e2e 保留 `typeof === 'string'` 防回归断言。

## 7. 每版的交付节奏

- 一个版本 = 一个 git tag（`v1.1.0` 起）+ 一份 `README.md` 更新记录 + 一条 e2e 基线（断言数只增不减）。
- 每次开工前先跑上一版门禁，基线红了先修基线，不带着红灯加功能。
- 每版结束按既有约定沉淀文档：翻车实录进坑库，系统性方案进前后端知识库对应技术目录。
- 冒烟/迁移 SQL 一律幂等（`information_schema + PREPARE`），Windows 下 mysql 客户端显式 `--default-character-set=utf8mb4`。

---

## 8. 明确不做（至少到 V2.0）

- 不做多仓多组织（现有 `warehouse_id` 已够单组织多仓）
- 不做自动补货 / 波次优化算法，先把"能跑对"做扎实
- 不做移动端，直到有真实 PDA 与现场流程
- 不做 WMS 与 ERP/TMS 的对接，直到有对接方与接口契约
